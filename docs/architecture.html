Hlekk

Old Norse for a chain link — a TAO-style object‑and‑edge database built on actors.

The infrastructure, not the application, owns partitioning, placement and capacity. Developers create objects in a logical database and never size, pick or reshard a Durable Object. A database that fits in one DO runs in one DO; the same code runs when it is five hundred.

Three kinds of component, and only three: a Worker that coordinates, one directory DO per database, and many host DOs that own vshards. Reads and writes go from the Worker straight to the hosts.

On the request path. One batched round per host, answered with everything that host read.

Delivered later by an alarm. The only eventually consistent edge in the system.

Control plane. Off the request path, driven by the directory.

Reported by alarm: storage bytes and request rate, for placement.

The three mechanisms the picture rests on

Identity, ownership, storage and read serving are separate concerns. An object’s ID never changes; the DO that owns its writes can. These three figures are the machinery that makes that separation hold.

What the platform forces

Most of the shape above is a response to five hard numbers. The vshard exists because a DO caps at 10 GB; batching per host exists because a DO caps at a thousand requests a second; BLOB IDs exist because JavaScript cannot hold a 64-bit integer.

And what v1 deliberately does not do: arbitrary SQL, ad-hoc joins or scans; transactions across colocation groups; incremental view maintenance and change subscriptions; regional read followers and R2 tiering. The changes log that all of those want is designed for and left out.
