A proposal for the Durable Objects platform team · from the Hlekk design

The layer every customer rebuilds

Durable Objects give an application a transactional, 10 GB SQLite database that can be placed anywhere. What they do not give it is a second one. The moment a customer's data outgrows one object, they write the sharding layer themselves — ID allocation, routing, rebalancing, cross-object consistency — and every one of them writes it differently.

This is a proposal to ship that layer: a TAO-style object-and-edge database in which the platform, not the application, owns partitioning, placement and capacity. It is built almost entirely out of primitives Durable Objects already have.

Where the boundary sits today

The three columns run the same application over the same storage. The only thing that moves is the boundary between what the platform operates and what the customer has to build and operate themselves.

Figure 2 · the build

One new component

The shape is a Worker that coordinates, one control-plane object per database, and many objects that own shards. Reads and writes go from the Worker straight to the object that owns the data; the control plane is consulted only when a cached route misses.

Fit

Designed against your published limits

Each of these numbers forced a decision rather than being worked around. They are the reason the design looks the way it does.

LimitWhat the design does about it
10 GB per SQLite-backed DOShards are capped near 1 GB, well under it, and one object holds many of them. The cap is set by how long a move takes, not by storage.
1,000 requests/sec per DO, softRequest count is treated as the scarce resource: everything a query can read without waiting is sent as one batched fetch per object, per tick.
2 MB row sizeThe object payload cap, surfaced to the developer as such.
Location fixed at creationChanging region is a shard move to a new object created with a locationHint or jurisdiction — the shard is the unit of residency.
Integers imprecise above 253 in JSIDs cross the wire as strings and are stored as 8-byte big-endian BLOBs, which also sort in unsigned numeric order, so one shard is one contiguous key range.

Build order

Riskiest parts first

01

One object

Schema, ID helpers, the write transaction, local execution. Measure per-object throughput first — it sets shard density, and therefore cost.

02

Control plane

Epoch checks and moved replies, the catalog, route caching in the isolate, and the coordinator end to end over many objects.

03

Shard moves

Stop-the-world moves under write load, with a harness that kills objects mid-move. The part most likely to be subtly wrong.

04

Automatic placement

Inverse edges through the outbox, then the allocator and the placement controller moving shards on storage and request pressure.

What this is not, and what would help

Out of scope, deliberately

  • Arbitrary SQL, ad-hoc joins and scans. The API is objects, edges, edge counts and ordered edge ranges, so every operation is cheap to route and cheap to cache.
  • Transactions across colocation groups. A transaction is anchored to one shard; everything it touches has to live there.
  • Incremental view maintenance and change subscriptions. Parked, with room left for them.
  • This does not replace D1. It is for the customers who outgrow it and who read graph-shaped data.

What the platform could add

  • A per-shard change feed. With an ordered log of mutations, a move copies a snapshot while writes continue and catches up on the tail, so the write pause shrinks from the whole copy to a few entries. Regional read followers would tail the same log.
  • A bulk key-range copy between objects, so a move is not a row-by-row read and insert.
  • A higher per-object request ceiling. It converts directly into shard density, which is cost per customer.
