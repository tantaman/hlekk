Architecture

Two ways to shard SQLite

Zerodha's Blobasaur and hlekk both spread data over many SQLite files with one writer each. Blobasaur stores blobs under keys the client chooses. Hlekk stores a graph under ids the database mints. Most of their other differences follow from that.

19 Nov 2026 · a reading of “Distributed, high-performance blob storage on SQLite”

Zerodha's tech blog has a good write-up of Blobasaur, the store behind the charts, layouts and preferences that Kite's users save. It's a sharded blob server on SQLite, written in Rust and speaking the Redis Cluster protocol. In production it serves reads and writes at a p99 of about 2 ms on three 4-vCPU machines. If you haven't read it, read it first, because this post follows its sections one by one.

Hlekk is built from the same parts. A database is many SQLite files, each file has exactly one writer, and a routing layer above them says which file holds what. What it stores is different. Hlekk is a TAO-style graph database: typed objects with JSON payloads, plus typed edges between them that are ordered by time and counted. A read starts from objects you already hold and follows edges as a tree of hops. It runs on Cloudflare Durable Objects, or in one Node process over a directory of files.

Read the two designs side by side and most decisions turn on one question: who names the data?

In Blobasaur the client does. HSET prefs user42 … stores under a key the application already had, and the server hashes that key to find it a place. In hlekk the database does. create returns an id, the id says where the object lives, and the application keeps it.

The rest of this post follows that split through sharding, schema, durability and rebalancing, and through the bugs each team hit.

01What each one needed

Blobasaur's list: Redis compatibility, so the existing Go and Python clients don't change. Single-digit-millisecond latency for both 2 KB settings and 5 MB chart layouts. Built-in compression. Simple CRUD with TTLs. Partitioning across machines. And relaxed durability, because the data is UI state: losing a recent write is “annoying” but “never affects trading.”

Hlekk's list, from its design document: stable 64-bit ids that survive moves between hosts and regions. Graph reads in as few network round trips as the data's locality allows. A database that grows from one host to many with no change to the application. Transactions within a colocation group, and inverse edges that are guaranteed to arrive eventually. And a small database that costs exactly one host.

Both lists keep the API small, for the same reason. Blobasaur rules out server-side scripting, complex data structures and secondary queries. Hlekk rules out scans, ad-hoc joins and arbitrary SQL. An operation that names its key, or its id, can be routed to exactly one place.

The lists part ways on durability and on what “grow” means. Blobasaur's data can afford to lose a recent write and hlekk's can't, for reasons covered under Durability. Blobasaur grows when an operator adds shards or nodes. Hlekk is meant to grow without anyone deciding to, which is why its shard layout is fixed when the database is created.

02Why SQLite

Both teams picked SQLite because it already does the hard parts of a storage engine: atomic commits, crash recovery and B-trees. You can also open any shard with the sqlite3 CLI to see what's in it. Blobasaur adds a performance argument: SQLite beats raw files for small blobs, and compressing first keeps 99% of stored values under the ~100 KiB point where raw files start to win.

Hlekk chose SQLite indirectly. What it chose was actors with durable local storage, and on Cloudflare a Durable Object's storage is SQLite. The design depends on two things the actor provides: one SQLite database per host, and one request at a time. The engine reaches storage through a small Sql interface (synchronous statements, one local transaction, and a size figure), so the Node adapter replaces a Durable Object's database with a file and changes nothing above it.

On language, Blobasaur left Go for Rust because Go's SQLite driver needs cgo, pins OS threads and adds GC pressure on multi-megabyte buffers. The result is a static binary with predictable memory. Hlekk is TypeScript with no runtime dependencies. The platform it was designed for runs JavaScript, and Node 22 ships node:sqlite. Hlekk's rows are capped at 2 MB, so multi-megabyte buffers on every request aren't its problem.

03Splitting data into shards

Blobasaur hashes twice. CRC16(key) % 16384 picks a Redis Cluster slot, and the slot picks a machine. Inside the machine, multi-probe consistent hashing picks one of N SQLite files. Each file has a dedicated writer task fed by a bounded queue, and a pool of read-only connections runs reads alongside it in WAL mode.

Hlekk doesn't hash anything, because an object's location is part of its id:

63
vshardbits 62–47 · 16 bits
sequencebits 46–0 · 47 bits, allocated per vshard

Bit 63 is always zero, which keeps every id below 263. Above that, SQLite turns an integer into a float and two different ids can compare equal. Ids are stored as 8-byte big-endian BLOBs.

Finding an object's vshard is a bit shift. Finding the host that holds the vshard is a binary search in a cached shard map. One host holds many vshards, and by default a new database starts with 64 vshards on a single host. So hlekk also routes in two steps. The difference is that its second step is a table rather than a function, and that's what makes moving data an online operation.

The step marked in orange is a function of the key, so changing it moves keys. The step marked in teal is a row in a table, so changing it moves one vshard and leaves every other one where it is.

What the id costs you is the ability to store an object under a key you chose. Zerodha's post gives exactly this as one reason it turned down SeaweedFS, which assigns its own ids and so needs a separate database to map them back to user keys. For Blobasaur that would put a second lookup on every read, since every read is by key.

Hlekk makes that trade deliberately and keeps the mapping inside the database: a global unique index, sharded by hash(value), whose entries are reserved first and confirmed once the object exists. The trade works for a graph because most reads never touch the index. You use it once to find where to start, and from there each edge carries the id of the next object.

In return, no object needs a lookup to find its shard, and a stale route gets corrected instead of returning a wrong answer. Because the vshard sits in the high bits, one vshard's rows form one contiguous key range in every table, so a move can copy a range without needing an index.

The sequence got most of the bits because it's the one field that can never be widened later: widening it would shift the vshard field and change the meaning of every id already minted. At 100,000 creates a second into one vshard (a bulk import, say), a 40-bit sequence runs out in about four months. A 47-bit one lasts about 45 years.

04How much sharding helps

In Blobasaur's benchmark, going from one shard file to sixteen on a single machine raised write throughput from 7,740 to 25,324 HSET/s. Reads barely moved, from 67,128 to 70,884 HGET/s, because WAL already let readers run alongside the writer. Shard files are how Blobasaur gets write concurrency on one machine.

In hlekk, vshards aren't a concurrency mechanism. All the vshards on a host share one actor, and the actor handles one request at a time. A Durable Object has a soft limit of about 1,000 requests a second. Hlekk gets more write concurrency by adding hosts, and uses vshards as the unit that moves between them. A vshard is closer to a Redis Cluster slot than to a Blobasaur shard file.

The two designs reached the same conclusion about commits. Blobasaur's writer takes a batch off its queue and commits it in one BEGIN IMMEDIATE … COMMIT. Hlekk commits each mutation in its own transaction. That's right for an application's write and wrong for a bulk load, as loading Simple English Wikipedia showed. Measured on one host over real SQLite, writing 20,000 edges:

From docs/wikimedia-demo.md. A deployed host measured about 570 edges a second one at a time, close to the workerd figure.

So assocAddMany writes many edges in one transaction. With it, the full load of 950,421 pages and 42,817,596 edges onto 43 deployed hosts took 21.1 minutes, at 33,832 edge writes a second across all hosts.

These numbers don't compare with Blobasaur's. Blobasaur's benchmark ran on tmpfs with the load generator on the same laptop, while hlekk's go over a network to Durable Objects. What carries over is the lesson: the commit is the expensive part, so batch it.

Hlekk has a placement question that Blobasaur doesn't. A hash has no locality to lose, and a blob store doesn't need any, since one GET reads one key. A graph read touches many objects, so placing related objects on the same host can save requests. On the Wikipedia link graph, the saving turned out to be small:

  • Placing each page by its first category, instead of by a hash of its title, cut the hosts that one page's links touched from 34.2 to 27.0 out of 43. That's 1.27x.
  • The same placement put 20.9% of all edges on one host. The loader keeps one batch in flight per host, so ingest ran 4.8x slower.

A page's categories describe the page, but its links point away from it, so there's little to colocate. For this graph, placing for locality cost a lot on writes and saved little on reads.

CREATE TABLE vshards (vshard INTEGER PRIMARY KEY, epoch INTEGER, state TEXT, next_seq INTEGER);
CREATE TABLE outbox (vshard INTEGER, seq INTEGER, target_vshard INTEGER, op TEXT,
                     PRIMARY KEY (vshard, seq)) WITHOUT ROWID;
-- and index_entries, for global unique lookups

Three differences matter.

Ids are 8-byte big-endian BLOBs, not integers. Big-endian bytes sort in numeric order, so one vshard is one contiguous range of the primary key. On Durable Objects an INTEGER column comes back as a JavaScript number and rounds silently above 253. If a BLOB misses a conversion, it fails loudly instead.

One table for every object type. Blobasaur gives each HSET namespace its own table, which fits well when the namespace is the only structure there is. Hlekk stores every object type in one objects table with a JSON payload, and its schema catalog works as a lens over that JSON. Seven of the eleven kinds of schema change it supports touch no rows at all, including adding a type, removing a field and renaming one. With a table per type, each of those would become DDL on every host, and a vshard would no longer be one key range across a fixed set of tables.

Counts are rows. COUNT(*) over a million-edge list is O(n), so assoc_counts is updated in the same transaction as the edge write.

On indexes, Blobasaur's single partial index on expires_at is the right size, and rows without a TTL cost it nothing. Hlekk measured what happens when a shared table collects many partial indexes, as it would if every team added one per type. SQLite checks every partial index's WHERE clause on every row written, whatever the row's type:

At 1,024 indexes, one insert takes about 3.3 ms, which limits a single-threaded host to about 300 writes a second. So hlekk keeps index entries as rows in an index_entries table. The write path already knows the object's type, so it writes only that type's entries.

06Compression

Blobasaur compresses with zstd. An average payload of 63.6 KiB is stored in 5.5 KiB, about 11x smaller. The post also does the page arithmetic: at SQLite's default 4 KiB page, that value shrinks from about 16 pages to about 2, which eases pressure on the page cache and the WAL.

Hlekk compresses nothing, because its rows are small. Across all 43.8 million rows of the Simple English Wikipedia load, storage came to 61.5 bytes per row and 2.69 GB in total. That's 1.04x what the payload sizes alone predict.

Hlekk had to do page arithmetic too, for a different reason. Each vshard is capped at 9 GB, just under a Durable Object's 10 GB storage limit. The cap only works if it's measured the same way the limit is enforced, and adding up payload sizes undercounted real storage by 1.05x to 4.7x. A payload sum misses keys, indexes and page overhead. It also misses overflow: a WITHOUT ROWID row too big for its page spills onto an overflow page and costs a whole page. At 4,096-byte pages, a 980-byte object cost 1.03 KB and a 1,000-byte object cost 4.7 KB. So hlekk compares page_count × page_size against the limit.

The 2 MB row cap is also the plainest reason not to use hlekk for Kite's workload. A 5 MB chart layout doesn't fit in one object.

07Durability

Blobasaur relaxes durability on purpose. It runs WAL with synchronous = NORMAL, so a power loss can drop recent commits while leaving each file consistent. Its optional async_write mode goes further and acknowledges a write as soon as it's queued, before the batch commits. For UI preferences that's a reasonable call.

Hlekk can't make that call, because its writes depend on each other. A single mutation commits the ownership check, the object or edge, the edge count, and any outbox row for the inverse edge, all in one local transaction. The host replies only after that commit is durable. On Durable Objects that's the platform's storage. The Node adapter sets no pragmas at all, so every commit gets SQLite's defaults: a rollback journal and synchronous = FULL.

Losing a recent write in hlekk could break two things:

  • Half of an edge pair. When an edge's inverse lives on another host, the forward edge and an outbox row commit together, and an alarm delivers the row later. Delivery is ordered per pair of vshards and safe to repeat: an add is an upsert and a remove only deletes what's there. That survives a crash only because the outbox row is part of the same durable commit as the edge.
  • A minted id. Ids get handed out and stored in other objects. Through hlekk's protocol they're also stored in other people's databases, as references like https://notes.example/db#281474976710691. If an acknowledged id were lost, it could be minted again for a different object.

Hlekk has a durability gap of its own, in the client rather than in storage. When a write lands but its reply is lost, the caller can't tell. Every mutation except create can be retried blindly. An edge add is an upsert, a remove only deletes what's there, and an update that carries the version it read comes back as a conflict. A retried create would make a second object, so the client reports the error instead of retrying. Whether create needs an idempotency key is still an open question.

08Scaling across machines

This is where the two designs come closest. Redis Cluster pre-shards the key space into 16,384 fixed slots and assigns slot ranges to nodes. A node asked about a slot it doesn't own answers MOVED. Hlekk pre-shards each database into vshards (64 by default, up to 65,536) and assigns them to hosts. A host asked about a vshard it doesn't own answers moved. Both put many small, fixed units behind a table, and both correct a stale route with a redirect rather than a wrong answer.

The differences are in who keeps the table:

  • One directory per database, not gossip. Each hlekk database has a directory that maps every vshard to a host and an epoch. It publishes the map in chunks, to Workers KV on Cloudflare or to a file on Node, and each reader caches only the chunks it has routed through. Even fully fragmented at 65,536 vshards, the map is about 786 KB.
  • Epochs, checked by the owner. Every request carries the epoch it routed with. The host compares that epoch with its own vshards row and refuses on a mismatch. The refusal doesn't say who the new owner is, so the caller asks the directory, which is the authority. A route is only ever a hint, and the owning host makes the decision.
  • The table changes at runtime. Blobasaur's slot assignment is static config, and its post says live rebalancing and automatic failover aren't built yet. Hlekk's map changes whenever the directory moves a vshard or opens new ones.

Neither system replicates data itself. Blobasaur's post doesn't describe a replication scheme. Hlekk leaves the durability and availability of a host's storage to the platform on Cloudflare. On Node it's one process over a directory, which you back up. Regional read followers are on hlekk's deferred list.

09Changing the number of shards

Blobasaur chose multi-probe consistent hashing so that going from 4 shard files to 5 moves about 20% of keys, instead of the ~80% that hash % n would move. The change is offline: stop the server, run blobasaur shard migrate 4 5 --verify, set num_shards, and start it again.

Hlekk never changes the mapping from an id to a vshard, because no function computes it. The design principle is “move, never split.” Capacity comes from moving whole vshards between hosts and from opening new vshards for new objects. An existing vshard is never divided. A move is a five-step state machine that the directory drives and resumes after a crash:

  1. Fence. The source host marks the vshard fenced. It refuses writes and keeps serving reads.
  2. Copy. The target host pulls the vshard's key range from each table, a chunk at a time, straight from the source. The directory records a cursor after each chunk.
  3. Install. The last chunk marks the vshard owned at epoch + 1. Until then the target serves none of it.
  4. Flip. The directory compare-and-sets the route to the target at epoch + 1.
  5. Retire. The source marks the vshard moved, answers moved from then on, and deletes the rows after a grace period.

Writes to that one vshard pause while it's copied. Reads keep working, and no other vshard is affected.

A placement controller in the directory watches each host's bytes and request rate. When a host crosses a threshold, the controller sheds a contiguous run of its vshards, so each move adds only one entry to the map. New objects go to an active set of vshards. A vshard leaves that set at half its cap and saves the other half for objects created alongside ones already in it. When the active set runs out, the allocator opens the next batch of vshards together (64 by default) and spreads them across hosts, so new writes don't all land on one host.

Blobasaur's approach is simpler and works today at its scale. Hlekk's has more moving parts. The copy is still stop-the-world for its vshard, but it goes a few megabytes at a time, so no single request has to hold a whole vshard, and a copy that dies resumes from the last recorded cursor. What hasn't been measured is a multi-gigabyte move on a deployed host, so how long a 9 GB pause really lasts is still an open number.

Blobasaur already has hlekk's answer, one level up. Redis Cluster's slots can move between nodes without rehashing a single key, because a slot is a fixed unit behind a table. Blobasaur hasn't built live slot moves yet, but the protocol allows them. The offline step comes from the level inside a node, where a consistent hash maps keys to N files. If a node's files held slot ranges instead, changing how many files a node has would be just another slot move.

10Proving the move was safe

Blobasaur moved off SSDB in phases. New workloads went straight to Blobasaur. Existing workloads then wrote to both stores for a month, with historical keys backfilled and reads falling back to SSDB on a miss, before the final cutover. The result was “zero discrepancies.” A month of production traffic checked against the old store is a strong test.

Hlekk has no predecessor to check against, so its test suite builds its own references. There are four kinds, across 675 tests:

  • A differential oracle. A query over a database spread across hosts must equal the same query against one host that holds every vshard. It's fuzzed over random graphs, queries and schemas.
  • A reference model. The write path, rebuilt in one process with no vshards, epochs or outbox, so every inverse edge and cascade lands immediately. Replaying the same workload into both catches a count that drifted or a cascade that stopped early.
  • Invariants across the whole cluster, checked during operations and at rest. For example: exactly one host serves each vshard, at the epoch the directory names, and every count equals the length of the list it counts.
  • A seeded simulation that interleaves writes, reads, partial outbox delivery, moves, moves that crash partway, rebalancing, and a network that drops and reorders messages.

Storage format changes work the same way. There's no in-place upgrade. Moving a vshard onto a host that uses the new format is the migration.

11What both teams learned

Each of Blobasaur's three lessons has a close counterpart in hlekk, and two of them are the same lesson.

Deletes don't shrink SQLite files

Blobasaur found freed pages piling up on SQLite's freelist. It fixed this with auto_vacuum = INCREMENTAL, a vacuum subcommand and a WAL checkpoint. Hlekk doesn't vacuum yet. Instead it budgets for the freelist: the 9 GB vshard cap leaves 1 GB of a host's 10 GB for things no vshard owns, including the freelist that deletes and retired vshards leave behind. A host also starts shedding at 8 GB, so the controller can act before a write hits SQLITE_FULL. Because size is measured in pages, the freelist counts against the host.

Pending writes have to be visible to every read

Some of Blobasaur's read paths skipped its map of pending writes, so a DEL followed by a GET could return the old value. Explicit tombstones, checked on every read path, fixed it.

Hlekk's simulation found the same kind of bug in the outbox. When an inverse edge's target vshard is on the same host, hlekk writes it inline in the same transaction, which makes colocated pairs atomic. But a move can bring two vshards onto one host while an operation between them is still queued, and then the inline write ran ahead of the queued one. Hlekk now writes inline only when nothing for that pair is queued. In both systems, a fast path skipped work that the slow path still had pending.

Cleanup has to share the writer

Blobasaur's TTL cleanup ran on its own write connection, as one large DELETE that held the lock. That pushed p99 write latency from under 5 ms to 30–50 ms. Running cleanup through the shard's own writer, in bounded chunks, fixed it.

Hlekk hit the general form of this rule and made it part of the schema: every row has exactly one writer. A pair of inverse edge types used to be writable from both sides, so the same row could be written from two vshards with nothing ordering the writes. A remove from one side and an add from the other could land in either order, and two adds with different times overwrote each other's sort key. Now exactly one side of every pair is marked maintained. The host refuses direct writes to that side, and the catalog rejects a schema that marks neither side or both.

Blobasaur's version of the lesson is about a lock and hlekk's is about ordering. Both come down to giving each piece of data one writer and sending every path through it.

12In production, and not

Blobasaur runs Kite on three nodes, each with 4 vCPUs and 8 GB of RAM. Through a trading session it holds p99 near 2 ms and p50 between 250 and 550 µs on every node.

Hlekk is at version 0.1.0 and has no production users. Its numbers come from deployed Durable Objects, and they measure a different operation: a Blobasaur GET reads one key from one file, while a hlekk read assembles a tree from several hosts.

  • In the Wikipedia pilot (2,000 pages on 43 hosts), the page card for “Country” showed 25 links from 17 hosts. It took 17 host requests and 95 ms, plus 28 ms to turn the title into an id.
  • In the fan-out test, a two-level read of about 500 objects over 128 vshards on 50 hosts took 61–81 host requests. The number of requests depends on hosts and rounds, not on how many objects come back.
  • The known slow case: a selective filter on a high-degree page reads the page's whole edge list. A filter over Country's links took 1,393 ms and 12 host requests, and there's no per-query scan cap yet.
  • All of Simple English Wikipedia is 2.69 GB across 43 hosts, about 63 MB each. At $0.20 per GB-month, Durable Objects storage for a 300 GB database would cost about $60 a month.

13The part Blobasaur doesn't need

Blobasaur speaks Redis so that existing clients don't have to change. Hlekk defines a new protocol so that databases run by different people can be read together. An edge can point into another database as <database URI>#<id>, and a read can follow it over HTTP into a database that decides for itself what to expose. The protocol has a normative spec, JSON Schemas, and a conformance suite that imports nothing from the implementation.

That's a separate subject from storage, but it explains some storage decisions above. It's why hlekk's ids have to be permanent, why an acknowledged id can never be lost, and why a database's URI can't change once it's been handed out.

14Which to pick

Use Blobasaur's design when values are opaque, addressed by keys you already have, sometimes several megabytes, and allowed to expire. Hlekk is the wrong tool there. It has a 2 MB row cap, no TTL, no compression, and no way to store a value under a key you chose.

Use hlekk's when the data is relationships, reads are trees of hops from things you hold, and the database needs to grow from one host to many without anyone resharding it.

On the rest, the two designs agree. Use SQLite as the unit of storage and give each file one writer. Batch your commits. Count pages, not bytes. And send every write to a given row through one place.
